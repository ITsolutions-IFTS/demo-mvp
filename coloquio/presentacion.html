modelAR

Plataforma para crear campañas con modelos 3D / realidad aumentada, publicarlas con QR y medir su uso.

ITSolutions AR · 5 integrantes · React · NestJS · PostgreSQL

01 · El problema

Mostrar productos en 3D/AR es difícil

  • Las marcas quieren que sus clientes vean productos en realidad aumentada, pero requiere apps nativas y desarrollo a medida.
  • No hay una forma simple de publicar un modelo y compartirlo (QR, link).
  • Y menos aún de medir si la gente lo usa.
02 · La solución

modelAR — campañas 3D/AR, multi-tenant

  • El cliente arma una campaña eligiendo un modelo del catálogo (Sketchfab + curados).
  • Se genera un visor AR + QR que se ve desde el navegador, sin instalar nada.
  • Se miden analíticas de uso (vistas, activaciones AR, clicks).
  • Todo multi-tenant: cada cliente y organización con sus datos aislados.

Frontend · Panel admin

React 19 + Vite + TypeScript

  • Pantallas: login, organizaciones, campañas (alta/edición), QR por campaña, colecciones, dashboard de métricas.

Frontend

modelar-web · Visor AR + QR

La experiencia que ve el usuario final

Frontend · Experiencia AR

AR en el navegador, sin app nativa

  • Flujo: Landing → Catálogo → escanear QR → Visor AR (/ar/:uid).
  • Visor: @google/model-viewer + three.js — ar-modes Scene Viewer / WebXR / Quick Look, con fallback de AR precisa.
  • Escáner QR: @zxing/browser lee la cámara; parseScanToModelId extrae el id del modelo.
  • Analytics: trackEvent fire-and-forget (keepalive) a POST /api/events.
Backend

modelar-api · Gateway (BFF)

El borde público entre el front y la lógica

Backend · API Gateway (BFF)

Backend-for-Frontend en Express

  • Gateway delgado (3 archivos): no tiene lógica, no toca la base, no valida el JWT.
  • Por qué existe: aislamiento/seguridad, separación de responsabilidades, deploy independiente, costura para varios frontends.
  • Cómo: reenvía method+body+headers (Authorization, request-id, IP), whitelist de rutas, timeout 10s → 503.
  • Trade-off honesto: para un MVP de un cliente, unificar sería más simple; lo separamos a conciencia.
Backend

modelar-core

El cerebro: toda la lógica de negocio y la base de datos

Core · Arquitectura

Clean Architecture (4 capas)

  • domain — modelo puro: entidades, puertos, errores. No depende de nadie.
  • application — casos de uso (32 en total). Acá vive la lógica.
  • infrastructure — adapters: Sequelize, cache, APIs externas.
  • modules — controllers + inyección de dependencias.
Core · Base de datos

PostgreSQL en Neon · Sequelize

  • 7 tablas, 11 migraciones + seeders. Core es el único que toca la base.
  • Multi-tenant: toda query filtra por client_id / org_slug.
  • Soft delete (deleted_at + paranoid); mapeo snake_case ↔ camelCase.
Core · Pruebas

Unitarias + integración · 86% cobertura

  • 31 unitarias — casos de uso con puertos mockeados (rápido, sin base).
  • Integración — repositorios contra un Postgres real: soft delete, paginación, aislamiento multi-tenant, FK.
  • E2E — la app completa con supertest.
