Guión hablado — 4 · modelar-api · Gateway (BFF) Integrante 4 · 5 min · Express · el borde público

El gateway: por qué existe y cómo reenvía el tráfico de forma segura.

① Qué es (arquitectura)

"modelar-api es un gateway muy delgado, en Express. Son literalmente tres archivos: la configuración, el arranque y el reenvío. No tiene lógica de negocio, no toca la base de datos, y ni siquiera valida el JWT — de eso se encarga core. Su único trabajo es ser la puerta de entrada pública del sistema."

② El concepto: Backend-for-Frontend (BFF) (decisiones)

"Lo pensamos como un patrón Backend-for-Frontend, o BFF. La idea del BFF es tener una capa de backend dedicada al frontend, que se ubica entre el cliente y los servicios de negocio, y que es el único punto de entrada para el front. Le da al frontend exactamente lo que necesita y centraliza ahí las cosas de borde —seguridad, CORS, tracing— sin meterlas en la lógica de negocio. Hoy reenvía casi uno a uno, pero esa capa es justamente la costura donde, el día de mañana, podríamos adaptar respuestas para distintos frontends —el panel admin y el visor AR público— sin tocar core."

③ Por qué existe separado de core

"¿Por qué no un solo backend? Cuatro razones. Seguridad por aislamiento: core queda como servicio interno y el gateway es lo único expuesto, con una lista blanca de rutas. Separación de responsabilidades: las cosas de borde viven en un solo lugar. Deploy independiente: cada servicio se despliega y escala por separado. Y la costura para múltiples frontends que mencioné. Para ser honestos: para un MVP de un solo cliente, un único backend sería más simple — esto es una inversión consciente en seguridad y en que el sistema crezca."

④ Cómo funciona (módulos / código)

"Cuando llega una request, la función forward arma la URL hacia core y reenvía el método, el body y una lista blanca de headers: el Authorization para que core valide el token, un x-request-id para tracing distribuido, y la IP real del cliente, que core usa para el rate-limit de los endpoints públicos. Le pone un timeout de 10 segundos; si core no responde —por ejemplo si está arrancando—, en vez de colgarse devuelve un 503 limpio. Además, en el arranque aplicamos helmet y cors, limitamos el body, generamos el request-id si no viene, y tenemos una lista explícita de rutas: lo que no esté en la lista devuelve un 404 sin llegar a core."

⑤ Decisiones de diseño

"Las decisiones: la whitelist de rutas reduce la superficie de ataque. El forwarding de la IP real es necesario porque, al pasar por el gateway, core vería la IP del gateway y no la del usuario — así el rate-limit por IP funciona bien. Y el x-request-id permite seguir una misma request a través de los dos servicios en los logs."

⑥ Fragmento representativo (código)

// forward.ts — reenvío al core con timeout
const upstream = await fetch(url.toString(), {
  method: req.method,
  headers,                 // authorization, x-request-id, x-forwarded-for...
  body: hasBody ? JSON.stringify(req.body) : undefined,
  signal: controller.signal, // abort a los 10s → 503
});
