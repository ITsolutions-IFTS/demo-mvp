Guión hablado — 5 · modelar-core + demo + Neon VOS · 5 min · NestJS · la demo es la columna vertebral

El cerebro del sistema y el cierre integrador. En 5 min, demostrá mientras explicás: lo que no entre, una frase.

① Qué es core

"modelar-core es el cerebro del sistema: un microservicio en NestJS y TypeScript que concentra toda la lógica de negocio, y es el único servicio que accede a la base de datos. No lo consume el navegador — lo consume el gateway, por HTTP/JSON."

② Arquitectura — Clean Architecture (arquitectura)

"Lo organizamos con Clean Architecture, en cuatro capas con dependencias en un solo sentido. En el centro, el dominio: entidades, los puertos —interfaces de repositorio— y los errores; es una capa pura, no importa nada de NestJS. Alrededor, la capa de aplicación, con los casos de uso, un archivo por operación. Después la infraestructura, los adapters: Sequelize, el cache, las APIs externas. Y los módulos, que hacen el cableado con inyección de dependencias. La regla de oro: el dominio no depende de nadie — eso nos deja testear la lógica sin levantar la base y cambiar de tecnología sin tocar las reglas."

③ Módulos principales (módulos)

"El core está dividido por áreas de negocio, y en total son 32 casos de uso. Cada módulo se ocupa de una sola cosa:

Autenticación maneja el login con JWT —un access token y un refresh token— y es multi-tenant.
Organizaciones representa a cada cliente, que es un tenant del sistema.
Campañas es la entidad central: la campaña con su modelo 3D.
Colecciones permite agrupar campañas.
Catálogo combina la API de Sketchfab con los modelos que nosotros curamos.
Y Analytics procesa los eventos que llegan del visor y arma las métricas."

④ Base de datos (base de datos)

"La base es PostgreSQL en Neon, con Sequelize. El esquema está versionado en 11 migraciones más seeders. Son siete tablas. Tres decisiones importantes: es multi-tenant, así que toda query filtra por client_id u org_slug — un tenant nunca ve datos de otro. Usamos soft delete: no borramos físico, marcamos una columna deleted_at. Y mapeamos snake_case en la base a camelCase en el código, dejando el modelo de Sequelize encerrado en infraestructura."

⑤ Decisiones de diseño

"Las decisiones más importantes de core. Ports and adapters: los casos de uso dependen de interfaces, no de la implementación concreta, y la inyección se resuelve con tokens. Errores canónicos: una jerarquía de errores de dominio que un filtro global traduce a un formato de respuesta uniforme, con código, status y request-id. Cache y rate-limiting con invalidación en cada cambio. Y una decisión de despliegue: como api y core están en el free tier de Render, que se duerme tras unos minutos, lo resolvimos con un health-check externo que los mantiene despiertos."

⑥ Pruebas (pruebas)

"El testing fue un foco. Tres niveles. Unitarias: 31, una por caso de uso, con los puertos mockeados — rápidas y sin base, aíslan la lógica. Integración: corren los repositorios contra un Postgres real; ahí validamos cosas que un mock no puede, como el soft delete, la paginación, que un tenant no vea las campañas de otro, y las foreign keys. Y un test end-to-end que levanta la app entera con supertest. La cobertura global es del 86%."

⑦ Fragmento representativo (código)

"El fragmento que elegí muestra la arquitectura en acción: la búsqueda de modelos, que mezcla nuestros favoritos curados con los resultados de Sketchfab. Acá se ve que el caso de uso no sabe de HTTP ni de SQL: recibe por inyección un puerto del gateway de Sketchfab y otro del repositorio de curados. Y tiene decisiones de diseño escritas en el código: los curados solo se insertan en la primera página, se deduplican los UIDs para no repetir un modelo, y como Sketchfab no da un total real, lo aproximamos." 
// línea 60 — set de UIDs curados, para deduplicar
const curatedUids = new Set(curated.map((c) => c.sketchfabUid));

// líneas 82-85 — resultados de Sketchfab sin los UIDs ya curados
const sketchfabFiltered = sketchfabResult.models
  .filter((m) => !curatedUids.has(m.uid))
  .slice(0, remaining)
  .map((m) => ({ ...m, isCurated: false }));

// líneas 91-94 — merge: curados primero, después Sketchfab
const data = [...curatedAsEntities, ...sketchfabFiltered];
return { data, pagination: { page, limit, total, totalPages } };

⑧ La demo end-to-end 🎬

"Y para cerrar, la demo en vivo, que es la prueba de que todo integra. Me logueo en la app productiva; eso valida un JWT contra core. Creo una campaña: cuando guardo, el request viaja del front al gateway y al core, core aplica las reglas y la persiste en Neon. La veo creada en la app. Y para demostrar la integración de punta a punta, voy a la consola de Neon y consulto la tabla campaigns: ahí está la fila que acabo de crear. Y esto no es solo a mano: está cubierto por los tests de integración automatizados que mencioné." 
SELECT id, title, sector, status, created_at
FROM campaigns WHERE deleted_at IS NULL
ORDER BY created_at DESC LIMIT 5;  -- la nueva sale primera
