01Qué es modelAR y cómo se comunican los 3 módulos

modelAR es una plataforma multi-tenant "app-less" de Realidad Aumentada web: una empresa arma campañas con modelos 3D, genera un QR, y cualquier cliente final abre ese QR desde el navegador de su celular y ve el modelo en AR sin instalar nada. Además hay un panel de métricas de interacción. Tres repos independientes, cada uno con un rol fijo:

modelAR-api

→SQL / Redis

El navegador nunca habla directo con core: todo pasa por el gateway. core es el único que toca la base de datos.

  • modelAR-web no sabe nada de la base ni de reglas de negocio: solo consume una API vía fetch/axios contra el gateway (con proxy de Vite a /api en local).
  • modelAR-api es un proxy fino: reenvía cada request tal cual al core (agrega x-request-id, propaga IP del cliente, aplica timeout de 10s → 503 si el core no responde). No valida JWT, no toca la base, no tiene lógica de negocio.
  • modelar-core concentra toda la lógica: auth, campañas, colecciones, catálogo, analytics, generación 3D. Es el único con credenciales de base de datos.

02Por qué 3 módulos separados (y no un monolito)

Pregunta esperada: "¿por qué no hicieron todo en un solo backend?"
  • Frontera de seguridad real: el único proceso con acceso a la base de datos y a Redis es core. Si mañana modelAR-web se sirve desde un CDN público y alguien intenta explotar el frontend, no hay ningún camino directo a la base: todo pasa por un proxy que no razona sobre SQL ni sabe qué es una campaña.
  • Contrato estable frente a evolución interna: el gateway expone una API pública fija; adentro, core puede cambiar de ORM, refactorizar casos de uso o reordenar capas sin romper a nadie que consuma el gateway.
  • Escalado y deploy independientes: se puede re-desplegar el frontend sin tocar el backend, o escalar el gateway (más tráfico público) sin escalar el core (más carga transaccional) de la misma forma.
  • Costura para crecer: sumar otro frontend (una app mobile nativa, un panel de otro cliente) implica consumir el mismo gateway, sin duplicar lógica de negocio.
  • Alineado con el equipo: 5 integrantes, 3 repos con dueños claros — cada quien puede iterar y deployar su parte sin bloquear a los demás (ver ramas activas por integrante en cada repo).

En términos de patrones: esto es el patrón API Gateway hacia afuera, combinado con Ports & Adapters (arquitectura hexagonal) puertas adentro en core.

03modelar-core — arquitectura y patrones de diseño

NestJS + TypeScript, arquitectura hexagonal (Clean Architecture) con 4 capas, dependencias en un solo sentido:

  • domain/ — entidades puras y puertos (interfaces de repositorio/servicio). No importa nada de NestJS ni de Sequelize.
  • application/ — los casos de uso (un archivo por operación: create-generation.use-case.ts, login.use-case.ts, etc.). Acá vive la lógica de negocio.
  • infrastructure/ — los adapters: repositorios Sequelize, cache Redis, clientes de APIs externas (Sketchfab, Tripo).
  • modules/ — controllers NestJS + wiring de inyección de dependencias (DTOs, guards, decorators).

Regla de oro: domain no depende de nadie → la lógica se testea con mocks, sin levantar una base real, y se puede cambiar de proveedor/ORM sin tocar las reglas de negocio.

04modelAR-api — el gateway

Node.js + Express, deliberadamente minimalista: 3 archivos en src/ (main.ts, proxy/forward.ts, config/env.ts), 4 dependencias de runtime (express, helmet, cors, dotenv).

  • Un único handler forward() reenvía las 32 rutas declaradas a CORE_URL usando fetch nativo (sin librerías de proxy).
  • Agrega x-request-id (tracing) y propaga la IP real del cliente para que el rate-limit por IP se aplique en el core.
  • AbortController con timeout de 10s → si el core no responde, devuelve 503 con un cuerpo de error uniforme.
  • /health hace un fetch al /health del core (timeout 5s) y responde {status:'ok', core:'ok'|'unavailable'} — siempre 200, informando el estado real del core en el body.
Honestidad para el Q&A: Helmet y CORS están con configuración default (CORS totalmente abierto), y el gateway no reenvía cookies en ninguna dirección — la autenticación viaja por header Authorization, no por cookie httpOnly. Es un gap conocido, no un olvido silencioso.

06Base de datos y por qué Neon

PostgreSQL gestionado con Sequelize, esquema versionado en 13 migraciones (no hay sync() mágico en producción). Tablas: clientsorganizationscampaignscollectionsanalytics_eventscurated_modelsrefresh_tokensgeneration_usagegeneration_jobs

Patrones de datos aplicados

  • UUID como PK en todas las tablas.
  • Soft delete: deleted_at + paranoid en campañas (no se borra físico).
  • Multi-tenant por clave denormalizada: org_slug/organization_id en vez de un esquema por tenant. Se detectó y corrigió un bug real de integridad (clientes con org_slug sin fila viva en organizations) con una migración de backfill + validación simétrica en collections/campaigns — buen ejemplo de "encontramos un hallazgo de diseño y lo resolvimos con datos reales", no teoría.
  • Índice único parcial en slug (permite reciclar el slug de una org borrada sin re-enganchar datos viejos).
  • Ledger append-only con 3 índices por eje de identidad (user_id/ip_hash/device_id) para contar cupos sin locks ni updates.
  • ENUM a nivel DB para estados (ej. generation_jobs.status).
  • Mapeo snake_case (DB) ↔ camelCase (código) aislado en la capa de infraestructura — el dominio nunca ve nombres de columna.
Pregunta esperada: "¿por qué Neon y no otra base en la nube?"
  • Postgres estándar, sin lock-in: es el protocolo de cable habitual, funciona directo con pg/Sequelize — cero reescritura de código vs. una NoSQL propietaria (DynamoDB, Firestore).
  • Serverless con scale-to-zero: no cobra por cómputo ocioso — clave para un proyecto académico sin presupuesto de infra.
  • Branching de base de datos: se pueden crear ramas de la DB (clon instantáneo) para probar migraciones sin arriesgar producción.
  • Free tier generoso sin tarjeta de crédito, suficiente para el volumen de una demo/MVP.

07Por qué Render (api + core) y Vercel (web)

Render para api + core

Ambos son procesos Node de larga duración: el core mantiene una conexión persistente a Redis y a Postgres. Vercel está pensado para funciones serverless con límite de tiempo de ejecución y cold-start por invocación — un mal fit para un proceso con estado y conexiones abiertas. Render da un contenedor persistente real (Docker-friendly), con /health propio.

Trade-off aceptado a propósito: el free tier de Render duerme tras 15 min sin tráfico. Se mitiga activamente (ver §10) — no es un problema ignorado.

Vercel para web

Es una SPA estática (build de Vite) que solo habla HTTP con el gateway — no necesita servidor propio. Vercel está diseñado exactamente para esto: CDN global, deploys sin configuración desde GitHub, y preview deployments por PR, muy útil para que las 5 personas del equipo revisen cambios de UI antes de mergear.

08Seguridad

  • JWT access + refresh con rotación: el refresh token se guarda hasheado con bcrypt en refresh_tokens — un leak de la base no expone tokens usables.
  • Passwords: bcryptjs (hash con cost factor, ver seeders/migración del superadmin).
  • Guards por rol (superadmin vs cliente) + validación de ownership por organización en cada caso de uso (parte del fix multi-tenant).
  • Rate limiting real en el core (@nestjs/throttler), no en el gateway — el gateway solo propaga la IP.
  • Validación estricta de entrada: ValidationPipe global con whitelist (descarta campos no declarados) + forbidNonWhitelisted (rechaza el request si vienen campos extra).

10Cómo se mantiene el sistema despierto (Render free tier)

El free tier de Render duerme un servicio tras ~15 min sin tráfico entrante; el próximo request paga un cold-start de 30-60s. Se resolvió con un health-check externo automatizado, no manual:

  • GitHub Actions (.github/workflows/keep-render-awake.yml en demo-mvp): cron: */5 * * * *, hace curl a /health de modelar-api y modelar-core en Render cada 5 minutos.
  • Como el /health del gateway ya hace fetch al /health del core, un solo ping externo verifica y despierta ambos servicios.
  • Iteración previa: un crontab personal (cada 10 min, script keep-render-awake.sh) que dependía de que una laptop estuviera prendida — se migró a CI porque no depende de ninguna persona, corre siempre en la infraestructura de GitHub.
Para el Q&A: es un buen ejemplo de "detectamos una limitación real de infraestructura gratuita y la resolvimos con automatización, no ignorándola ni pagando un plan pago innecesario para una demo académica".

11White-label: cómo funciona realmente

Cada Organization tiene un campo sector (ecommerce | turismo | educacion | inmobiliario | museo) — un único campo, mínimo, que vive en el dominio/DB del core. Todo lo demás es puramente de presentación, resuelto en el frontend, en un mapa SECTOR_UI:

SectorLabel de colecciónCTA
EcommerceCategoría / Categorías"ver producto"
TurismoDestino / Destinos"más info"
EducaciónSerie / Series"ir al sitio"
InmobiliarioProyecto / Proyectos"ver unidades"
MuseoSala / Salas"más info"

Una función enrichOrg() combina la organización real (que viene de la API) con esta tabla de UI, en el cliente. El comentario del propio código lo deja explícito: "estos campos NO viven en la API... son decisiones de presentación que cada cliente del web aplica localmente" — mantiene el dominio mínimo en el core y evita ensuciar la base con strings de interfaz.

Resultado concreto: un museo y una inmobiliaria comparten exactamente el mismo motor (auth, campañas, colecciones, analytics, la tabla collections es literalmente la misma), pero uno ve "Salas" y el otro "Proyectos" para la misma entidad.

Alcance honesto: hoy el white-label cubre terminología + color de acento por sector (un preset fijo de 5 sectores), no todavía logo/dominio propio por tenant. El próximo paso natural para un white-label "completo" es agregar campos por organización (logo_url, primary_color, custom_domain) y aplicarlos en runtime — misma arquitectura (una capa de presentación por org), solo que respaldada en DB en vez de un preset estático por sector.

12El desarrollo a medias: generación de modelos 3D con IA

Hoy los modelos 3D salen de buscar en Sketchfab (biblioteca externa) o de un catálogo de curados propios (curated_models, con source: sketchfab | local). La evolución en curso es permitir que el propio cliente genere su modelo 3D con IA (a partir de texto o de una imagen) en vez de depender de un banco de modelos ajeno.

Estado real: en modelar-core, sobre la rama feat/catalog-category, existe una arquitectura completa para esto — pero el 100% de esos archivos aparece como untracked en git: nunca se commiteó. Es exactamente el "desarrollo local a medias" que hay que terminar.

Lo que ya está construido hecho

  • Dominio completo: GenerationJobEntity, GenerationStatus, Plan (hoy todo es FREE, el cobro no está implementado), puertos IGenerationJobRepository, IGenerationUsageRepository, IAssetStorage, I3DGenerationProvider.
  • Casos de uso: crear/consultar/listar generaciones + GenerationQuotaService (cupo gratuito mensual, GENERATION_FREE_MONTHLY_LIMIT=3, contado por la unión de user_id / ip_hash / device_id — cubre tanto usuarios logueados como anónimos).
  • Adapter real funcionando: TripoGenerationProvider contra la API de Tripo3D (OpenAPI v2), con tests, más un FakeGenerationProvider (default) para desarrollar sin gastar créditos.
  • Storage swappeable: PassthroughStorage (default, devuelve la URL del proveedor tal cual) y R2Storage (Cloudflare R2, re-hosteo durable) — elegibles 100% por env var, sin tocar casos de uso.
  • Persistencia: migraciones 12-generation_usage (ledger append-only) y 13-generation_jobs (provider, kind, prompt/imageUrl, status, progress, model_url/thumbnail_url).
  • API: POST /generation (texto o imagen, 402 si agotó cupo, throttle 10/min), GET /generation, GET /generation/:id (poll de progreso).
  • Tests: specs de casos de uso, del cupo, del adapter de Tripo, y hasta un e2e.

Lo que falta pendiente

  1. Commitear el módulo — hoy es puro working tree local; no existe en ningún remoto ni en master. Se pierde si no se resguarda ya.
  2. Wire en el gateway: modelAR-api whitelistea 32 rutas y ninguna es /api/generation — sin esto, el front no puede llegar al endpoint aunque exista en el core.
  3. UI en el frontend: no hay ninguna pantalla de generación (prompt/imagen → esperar → ver resultado); modelAR-web no tiene código relacionado.
  4. Storage productivo sin aprovisionar: R2Storage falla rápido si faltan envs (R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_BUCKET, R2_PUBLIC_BASE_URL) y ninguna está en .env.example — hoy correría en modo passthrough, con URLs de Tripo que caducan.
  5. Cerrar el loop hacia el catálogo: el resultado (model_url/thumbnail_url) queda en generation_jobs pero nada lo persiste automáticamente como un curated_models con source=local — ese paso conectaría "generé un modelo" con "me aparece en el catálogo para usarlo en una campaña".

Próximo paso concreto, en orden

  1. Commitear + pushear el módulo generation a una rama (protege el trabajo ya hecho).
  2. Sumar las 3 rutas de /api/generation a la whitelist del gateway — mecánico, mismo patrón que las 32 rutas existentes.
  3. Aprovisionar un bucket de Cloudflare R2 (free tier: 10GB + sin costo de egress) y cargar las 5 env vars — sin esto el passthrough es un riesgo real.
  4. UI mínima: formulario (prompt o imagen) → POST /generation → poll GET /generation/:id → mostrar el GLB en el mismo <model-viewer> que ya se usa para Sketchfab (cero componentes nuevos de visualización).
  5. Conectar el resultado exitoso a curated-models (source=local) para que el modelo generado sea reutilizable como cualquier otro del catálogo.

13Por qué Tripo (y qué alternativas gratuitas se evaluaron)

El puerto I3DGenerationProvider se diseñó agnóstico a propósito — el propio código lo dice: "denominador común que cumplen TODOS (Tripo, Meshy, Hunyuan3D...): polling". Se evaluaron varias opciones y se arrancó implementando Tripo3D por motivos concretos:

  • Free tier real: 300 créditos/mes sin tarjeta de crédito — alcanza para una demo académica sin gastar un peso.
  • API REST simple, async job + polling: encaja 1:1 con el patrón createJob/getJob que ya se necesitaba para no bloquear el request HTTP mientras el modelo se genera (puede tardar decenas de segundos).
  • Texto→3D e imagen→3D con el mismo endpoint: cubre ambos casos (kind: 'text' | 'image') ya modelados en el DTO, sin dos integraciones distintas.
  • Exporta GLB (con PBR opcional): mismo formato que ya consumen @google/model-viewer y el GLTFLoader de Three.js en el visor existente — cero cambios en el pipeline de renderizado AR.

Alternativas ya contempladas por la abstracción (solo requieren un nuevo adapter, no tocar casos de uso)

OpciónTipoPor qué se consideró / cuándo tendría sentido
MeshyCloud, free tierTambién sin tarjeta, exporta 7 formatos (incluye GLB) — buen respaldo o comparación de calidad frente a Tripo.

Hunyuan3D-2 / TRELLIS / Stable Fast 3DOpen-source, auto-hospedadoSin costo por modelo generado, pero requieren GPU propia. Tiene sentido migrar acá si el volumen crece y el costo por-modelo de las APIs cloud deja de ser conveniente — la arquitectura ya lo permite sin reescribir nada del lado del core.
La frase para el jurado: "no apostamos a un solo proveedor: diseñamos un puerto común y hoy tenemos el adapter de Tripo funcionando; si Tripo cambia sus precios o límites, swappear a Meshy o a un modelo open-source auto-hospedado es una variable de entorno, no una reescritura."
